# 供货、资金与售后详细设计

## T11 供货

两类供方：电脑，卡／订阅。平台自营也建立supplier身份，使用相同任务和验收；一家供方可具备两类能力。指定账号开通是卡／订阅侧的任务，不固定设第三类开通供应商。

供应商可由管理端建号或自助申请，审核后开供货权限。电脑登记不等于可售；资源验收包括配置、地区、初始环境、真实连接、维护、导出和清理。卡／订阅资源登记脱敏外部引用、支持服务、付款／开通能力、币种、成本、交付时间和售后，不采集普通页面展示的完整卡号／CVV。

派单只选approved且能力覆盖的供方，成本和交付时间是内部匹配条件；客户购买的是电脑与AI套餐，不替供方选择承担额外费用。任务先offered→accepted／working→reported→平台核验verified。API接入和人工回报都不能跳过验收。

电脑供方准备主机，订阅供方处理指定邮箱（平台准备或客户提供）的开通。账号身份、需要的认证、付款和实际登录按真实流程分别核验；平台管理任务、结果、成本、上游截止和客户交付单元。有卡、扣款成功、可登录、订阅可调用不是同一状态。同卡能开多少账号取决于真实供方／服务规则，不设置无限复用假设。

平台直接开卡、充值、冻结、销卡不是已确认必需功能。原始卡操作由供方管理；提供付款卡不自动意味可以完成KYC或开通订阅。平台不绕过官方认证，不自动接受未经核验的交付模式。

取消／改套餐后收到迟到开通结果：记录成本与真实状态，不交付给已取消客户；回收涉及真实账号处理，不把一个客户认证令牌随意复制给另一个客户。

多台采购分别记录每台的指定AI账号，平台准备时逐台生成目标，客户提供时逐台确认；unitOrdinal＋provider确定任务目标。当前实施默认不自动共用一个订阅账号；同一卡能否支付多个不同账号仍由真实供方规则决定，两种关联不能混为一谈。

## 订单异常决策

| 阶段 | 情况 | 系统行为 |
| --- | --- | --- |
| 付款前 | 无正常供货能力 | 缺货展示／提醒，不收预约款 |
| 付款后未交付 | 正常准备中客户取消 | 未产生上游实际开通费用全退；有成本由管理端核定、客户确认可退额 |
| 付款后未交付 | 平台开通失败 | 客户选继续等待、退该套、或退AI改纯电脑；等待不起租 |
| 多台订单 | 一套失败 | 只影响该单元，其他已交付电脑继续 |
| 已有有效电脑加购AI | 开通中 | 电脑继续可用；等待补电脑时间，AI原承诺截止不延 |
| AI加购未交付失败 | 原电脑已在租 | 处理新增AI订单项，不自动退掉原本有效电脑 |
| 已交付正常服务 | 客户主动不用／换购 | 旧剩余费用不退不抵；主动换购新单全价、AI重新选择 |
| 故障换机 | 客户选择继续履约 | 原lease与权益延续，更换allocation，不按主动换购再收全价 |

供应成本上涨不自动向已成交客户补差。成本、平台售后支出、供应商追偿分别入账；未约定的上游退款或扣结算款不能凭系统规则创造。

## 租期和AI承诺的计算

初次交付：电脑与所购AI整套验收开放时间为电脑和本套承诺起点。上游实际截止须覆盖对客户承诺的期间，不足不能标ready。

加购：付款确认时冻结原电脑截止作为本次AI promisedUntil，并冻结实际承诺起点／期限快照；标准30天价格全收，即使电脑只剩20天或1天。前端展示准确截止和费用，服务端记录条款哈希。实际可用始于开通验收，正常等待按已定规则补电脑时间，不能反向延长AI期限。电脑补时后形成的额外期间可以没有AI。

提前续费：原周期仍有效AI不会被立刻取消。新周期的AI选择作用于续费段；选择只续电脑不赠送下一段AI。AI续订必须核验上游能覆盖新的承诺段，不能靠改平台日期伪造覆盖。

## T10 工单与赔付

只有客户提工单才进入故障补偿流程；平台仍持续监测维修。系统采样作为证据，管理端核实责任、故障区间和修复状态，系统计算并执行。提单时间与故障开始时间分别记录，不能用提单时间吞掉已核实此前故障。

1. computer_fault：核实设备责任故障及区间；符合申报资格则增加电脑时长，原AI截止不变；对同一受影响区间内实际购买且承诺期有效的AI另做现金赔付。
2. ai_fault：先进入可配置修复窗口；窗口内修好不退。超窗仍未修好，按核实故障起点至本次原承诺截止的未提供部分退款，包含等待维修期，并终止该AI的平台交付；有效电脑和另一AI继续。
3. 严重电脑故障：客户选替代机履约，或结束该套并退未提供的电脑与所购AI。结束电脑同步结束关联AI平台交付，同单其他单元不受影响。
4. 退款回原付款订单／渠道／付款人。子账号提单不能改变原付款人。平台退款不等于官方允许按天取消上游订阅。
5. 电脑补时申请须在原记录规则“电脑到期前至少3天”提交；不能擅自改成到期前任意一天。最后3天新故障的普通补时无新增例外；维修和既定AI退款分别处理。

## 区间去重和金额算法

对某AI：先将核实区间裁剪到原承诺区间 [promisedFrom,promisedUntil)，合并重叠／相邻区间，得到累计不可用毫秒U。原实付P、原承诺时长D固定：

`累计应退 = floor(P × U / D)`

`本次新增退款 = max(0,累计应退 − 已成功退款 − 已预留退款)`

使用BigInteger／BigDecimal精确计算，不以每日先四舍五入再累加。例：300元承诺20天，核实1天不可用，退15元。两张工单重叠同一天不能退两次。终止剩余期时合并此前区间及已退款，累计不超原实付。

电脑补时同样按核实区间并集计算新增量，source事件唯一；正常等待与故障重叠不重复补同一时间。不同原因计入同一租约补偿总账。AI赔付和电脑补时是两种已确认补偿，可以对应同一故障，不能将两者误当重复。

## 收款与退款适配

目标渠道支付宝、微信、国际卡和PayPal。PaymentProvider需有createPayment、queryPayment、refund、queryRefund、verifyWebhook；未配置渠道不可展示可真实支付。native回跳和网页显示都只触发服务端查询。

回调验证商户、签名、订单、币种、金额、事件去重，再进入T04。数据结果未知先查渠道，不能换新请求重复扣费／退款。渠道没有幂等支持时记录externalRef并保守对账，不承诺跨系统exactly-once。
