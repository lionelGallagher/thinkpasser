# 浏览器会话与原生适配边界（候选设计）

平台只接受已认证服务端主体；浏览器提交的 `accountId` 不能决定身份。切换已登录账号时使用该账号现有登录上下文重新请求授权；不把多个账号合并为一个可访问所有设备的主体。主账号管理子账号和设备，不因此取得子账号的桌面权限。

本文件是待接入产品后端和原生端的契约。进程内 `SessionAuthority` 只验证业务状态机；它不是已部署身份系统，也不是设备上的完整验签器。

## 会话建立与接管

1. 浏览器在内存生成临时密钥，以认证登录上下文请求 `POST /devices/{id}/sessions`。服务端检查租户、账号有效、独享绑定、租期和设备状态。请求只携带设备标识、临时公钥指纹、客户端类型等；不接收任意 RustDesk ID、密码或中继地址。
2. 服务器原子检查账号和设备的当前会话。有旧会话时返回 `409 TAKEOVER_REQUIRED` 和当前会话 ID。用户明确确认后带该 ID 重试；数据库事务必须比较当前 ID，防止把过期确认用于另一个新会话。
3. 确认后增加设备会话 epoch，撤销旧会话，向设备发送撤销。设备释放已按下的键鼠、关闭旧输入/画面/音频/文件通道，但保持远端应用运行。**设备确认旧通道关闭后，新会话才能从 pending 进入 active。** 本目录的内存参考状态机没有这条真实设备确认链路。
4. 平台签发短时 grant，包含版本、issuer、audience=`device:{id}`、账号、租户、session ID、epoch、jti、iat/exp、能力白名单、临时公钥指纹。参考实现用 Ed25519；生产需增加 `kid` 与公钥轮换。grant 不放 URL、日志或长期本地存储。
5. 被控端/网关检查平台签名、audience、时间、设备绑定代次、当前 session/epoch、jti 一次性使用，并通过新通道挑战签名证明浏览器持有对应临时私钥。把设备身份、浏览器密钥、session/epoch、双方通道指纹绑定进挑战。**参考代码只比较指纹字符串，没有实现密钥持有证明。** 在补齐前不可作为生产接入验证。
6. 双方交换经过授权的会话信令。原生适配器必须固定可信设备身份/根公钥；验证 RustDesk SignedId/DTLS 指纹绑定；拒绝上游可选的无可信公钥/非安全回退。业务 grant 不能塞进旧 password 字段并假定被控端已懂；需新增产品协议消息或原生接入钩子。

所有桌面入口（网页、Windows/Mac 原生、直接/中继、重连及文件通道）都验证同一授权。每台机器可保留受控的 RustDesk 连接密码；原生端不能开放仅凭设备 ID 和永久密码绕过平台租约、分配及会话授权的旁路。内置 RustDesk 身份/密码验证与平台账号授权是两层检查，设备连接密码不是平台登录密码。

## 设备连接凭据与租约关联

建议由稳定机器 ID 关联交付单元、当前租约、使用账号／分配版本和凭据版本。备机时设置每机独立凭据并验证；正常续费保留环境、更新租约，旧到期任务须因版本变化失效。到期拒绝新会话并主动关闭旧会话，改密结果与会话关闭分别确认；三天保留期只开放受限导出。换使用者前撤销旧授权并轮换凭据，文件软件环境按主账号保留／重置选择处理，私人登录凭据独立清理；到期回库和下一租约则核实完整清理结果。

后台保存安全引用及版本，不把永久密码放进 URL、日志或共享镜像。建议电脑列表一键连接，不默认在普通界面展示长期密码；界面是否展示仍属实施建议。设置／轮换接口和原生强制检查尚未实现，不能把本机密码参数当作已有云端管理 API。完整关系见[技术架构总览](../../docs/architecture.md)。

## 租期、重连与撤销

参考策略为 10 秒续租、30 秒会话租约、grant 单次使用；这些是工程初值，需按海外网络压测调整。浏览器断线后重新拿当前 session 的新 grant，并重新证明临时密钥持有；断线超过租约需新建会话。浏览器刷新丢失临时密钥时，按新连接走确认接管。

设备本地维护已验签租约的截止时间，用单调时钟计时；控制平台不可达时到期关闭控制与输出通道，不影响远端程序。服务端账号停用、解绑、到期、接管都主动撤销；设备本地期限是撤销通知失败时的上限。离线设备恢复后先同步绑定与 epoch 再接受连接。生产的 jti、epoch 和独占会话必须持久化，跨进程由数据库事务/带 fencing token 的锁协调，不能使用本目录的 Map 代替。

媒体和输入共用同一有效会话。大文件分块需要 job ID、块序号、大小上限、哈希、取消、授权复验与受控路径；旧会话撤销时同时取消传输，不能建立一个永久有效的独立文件 token。设备重启和重装走单独管理 API：主账号可重启旗下设备，子账号仅自己的设备；重装仅主账号，并使用产品规定的清空确认。它们不是任意 Misc/TCP/终端消息转发。

## 原生适配器接口

```text
connect(verifiedGrant, channelBinding) -> pendingSession
confirmPreviousSessionClosed(epoch) -> activeSession
onEncodedVideo(codec, display, keyframe, pts, bytes)
onSystemAudio(format, opusBytes)
onCursor / onClipboard / onFileProgress
sendAuthorizedInput(parsedMessage)
transferAuthorizedFile(job)
renew(verifiedGrant) / close(reason)
```

接口尚无对应的稳定上游 headless SDK；需要在固定 fork 内分离 UI 回调和会话核心，或给同机 RustDesk 被控服务增加受保护的私有接口。`gateway-session.mjs` 只定义了 `send/close` 最小接口并用 stub 测试。它未创建 nativeProvider，也不能执行真实桌面控制。

## 部署位置候选

| 方案 | 明文与密钥位置 | 媒体路径/资源开销 | 当前缺口 |
| --- | --- | --- | --- |
| 被控 Windows/Mac 侧适配器 | 浏览器与被控电脑侧处理桌面明文；业务云只授权/信令 | 尽可能直接 WebRTC；失败可用只转 DTLS 密文的 TURN。复用压缩帧时可避免重复编解码；多一个本机进程、加密及队列内存；标准 RTP 路线另需分包与反馈 | 本机安全 IPC/原生钩子、浏览器协议内核、自己的授权信令、部署签名、Mac 权限、Windows 提权输入、TURN；尚未真机证明 |
| 云端原生网关 | 网关作为 RustDesk 控制端解密，能看到桌面、输入、剪贴板、文件与系统声音 | 远端→网关→浏览器。可转发兼容编码帧；需转码时额外 CPU/GPU 和延迟。会话隔离及每路资源限额 | headless 核心抽离、可信执行范围、密钥托管、地域与容量、成本；客户尚未选择这种信任模型 |
| 浏览器直接实现 RustDesk 原生协议 | 明文与会话密钥仅在浏览器和被控端；仍需有根的身份/指纹验证 | 不需要额外转换进程；传统 WSS relay 或补齐信令后的 WebRTC DataChannel | 未公开 JS 内核须自行完整实现：认证/加密、输入、编解码、剪贴板、文件、音频、重连；工作量最大 |

被控侧方案也不能单凭“WebRTC”三个字对外承诺端到端加密：需要验证设备身份、信令抗替换、密钥持有、授权绑定、密钥生命周期与中继确实不终止 DTLS。当前合成原型没有做这些验证。云端方案不能称为浏览器到被控电脑之间、网关不可见的加密。

按单向媒体有效载荷 R Mb/s 计算，每小时约 `0.45 × R GB`。直连只经过设备到浏览器一条主要媒体路径；TURN 需收发各一份，处理总流量约 `0.9 × R GB/h`；云端网关同样有两段媒体路径，并可能承担网关外发费用。实际结算看供应商出入站口径、协议开销、音频/文件、转码码率和流量包，本阶段没有采购或价格估计。

建议先把被控侧的“复用 RustDesk 已编码帧 + 自有授权信令 + DataChannel + 浏览器解码”做成真机技术验证，按 Windows/Mac 两端的实际资源、权限和网络兼容性再确定架构。两种网关位置均保留为候选，不默认客户桌面可交由云端解密。
